## 3. 已确认的其它文本问题

### 行首附点吞音

[_strip_leading_measure_label()](/D:/CODE/MyProjects/score_trans/backend/score_trans/domain/parse/jianpu_text.py:1007) 会把行首 `2.`、`3.`、`7.` 误判为小节编号。受影响行：微信图1物理行 4、7、12、13、15；page_005物理行 17。例：`2. (s5 s4) h0 |` 重解析后首个 `2.` 被删除。微信图1源 pitch 175、重解析 170；page_005 少 1 个 pitch。

### 长 `-` 休止和双附点

长休止实际出现在 page_001 的 `0-----------`，page_005 的 `0----------`/`0---------------------`，page_007 的 `0----------`/`0-------------------`，以及 page_004 的 `s0----`、page_006/微信图1的 `q0--`。项目文档规定每个 `-` 延长一拍，因此这些 token 是语法可解析的，但出版形式畸形，也说明源时值被压成了单线文本。

双附点共 8 个：微信图1 6 个 `0..`，page_007 2 个 `q2..`。当前语法允许双附点，属于可读性/时值吸附风险，不是未知 token。

page_001 的 `$6:4;\pph[...]`、`^fh[...]` 等紧凑前缀也能被当前 `_parse_tuplet_token()` 解析，属于可读性问题而非已证实的语法错误。

## 4. XML -> 简谱对应

### 重跑确定性

对 10 个 XML/MXL 使用当前代码的 `musicxml_path_to_scores(..., target_key="auto")` 和 `scores_to_jianpu_text()`，在 `PYTHONHASHSEED=1/2/3` 三个独立进程下，10/10 哈希稳定且与存储文本逐字一致。

当前 pipeline 入口默认 `target_key="C"`（[actions.py](/D:/CODE/MyProjects/score_trans/backend/score_trans/exec/pipeline/actions.py:93)，API Form 也为 C），而前端设置默认是 auto。用 C 重跑时，正好 page_002、page_003、page_005、page_008、微信图2 五个非 C 调文件与存储不同。这解释了外部报告的 5/10，不支持“当前纯转换函数随机”的结论。

### 调号

首个 XML `<key>` 分别为：page_002=1(G)、page_003=-2(Bb)、page_005/page_008=-1(F)、微信图2=-2(Bb)。page_001、page_004、page_006、page_007 和微信图1没有任何 `<key>`，共 5 个，auto 回退 C；这是已确认的风险，但实际曲调是否不是 C 需要原谱或图片才能判定。

### 显式还原号 `n`

当前 `_parse_pitch()` 将 `n` 存成 `accidental=0`，没有抵消调号。非 C 调中重新导出会变成带调号的降音。明确受影响的 token：page_003 Bb 59、page_008 F 21、page_002 G 43、微信图2 Bb 14、page_005 F 21，合计 **158 个**。例如 Bb 调 `n1` 重新导出为 B-flat，而不是 C natural。

重导出 pitch multiset 的差异如下：page_002 缺/多 43/43，page_003 59/59，page_005 36/35，page_007 2/2，page_008 29/29，微信图1 5/0；其余文件在该集合比较下相等。

### 多声部不可逆

10 个 XML 都有至少两个 voice。当前代码保留 `event.voice`，但只按 staff 切分；writer 在 [jianpu_text.py](/D:/CODE/MyProjects/score_trans/backend/score_trans/domain/write/jianpu_text.py:167) 线性遍历 `measure.events`，简谱文本没有 voice 标记。多个声部被串进同一条时值线，导致大量超拍/少拍和结构错位。
